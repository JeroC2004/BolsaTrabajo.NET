# Guía para estudiar la defensa

## Cómo recorrer el proyecto

El sistema tiene una API central y dos interfaces que la consumen: Windows Forms (escritorio) y Blazor WebAssembly (navegador). Las pantallas llaman a los clientes HTTP; estos envían DTO a los endpoints. Los endpoints delegan los casos de uso en los servicios, que utilizan repositorios para acceder a SQL Server mediante Entity Framework Core.

Flujo habitual: **pantalla → ApiClient → endpoint → servicio → repositorio → DbContext → SQL Server**. La respuesta vuelve por las mismas capas. Domain.Model contiene las entidades y sus reglas; DTOs contiene los contratos que se intercambian por HTTP.

Para seguir un ejemplo concreto, leer Ofertas.razor o OfertaLista.cs, OfertaApiClient.cs, OfertaEndpoints.cs, OfertaService.cs, OfertaRepository.cs, Oferta.cs y finalmente BolsaTrabajoContext.cs. En una creación, la pantalla arma el DTO, la API verifica permisos, el servicio construye la entidad y comprueba referencias, y el repositorio guarda el registro.

## Ideas para explicar oralmente

- **Separación de responsabilidades:** las pantallas presentan e interactúan; los servicios coordinan casos de uso; los repositorios encapsulan consultas; las entidades protegen sus valores.
- **Interfaces e inyección de dependencias:** los contratos permiten consumir operaciones sin construir la implementación concreta. WebAPI/Program.cs registra qué clases se entregan a cada constructor.
- **DTO frente a entidad:** el DTO transporta información; la entidad expresa el modelo del negocio. MapToDTO adapta la representación interna al contrato de salida.
- **async/await:** permite esperar operaciones de red y base de datos sin bloquear innecesariamente la ejecución. Un Task representa una operación pendiente; no implica crear un hilo por llamada.
- **Entity Framework Core:** DbSet representa conjuntos de entidades, LINQ expresa consultas y SaveChangesAsync persiste los cambios. Include carga relaciones; AsNoTracking evita seguimiento en consultas de solo lectura.
- **Migraciones:** conservan cambios del esquema. Up los aplica, Down define la reversión y el snapshot sirve de referencia para generar la próxima migración. El seeder carga datos, que es una responsabilidad distinta.
- **Autenticación y autorización:** el inicio de sesión genera un JWT firmado. La API verifica firma, emisor, destinatario y vencimiento; las políticas controlan roles y los endpoints comprueban pertenencia a alumno o empresa. Ocultar botones no reemplaza estos controles del servidor.
- **Contraseñas:** Usuario guarda hash y salt; ValidatePassword deriva el hash de la contraseña recibida para compararlo. El token de sesión es diferente de la contraseña.
- **Postulaciones:** el servicio verifica existencia de alumno y oferta, que la oferta esté activa y no haya vencido, y que no exista una solicitud duplicada. La base agrega un índice único alumno/oferta.
- **Currículum:** el PDF se almacena como contenido binario con metadatos; consultar el resumen evita descargar todos los bytes cuando solamente se necesita mostrar información.
- **Herencia y reutilización:** las clases parciales de Windows Forms separan diseño y lógica; los formularios base de catálogo y el reporte genérico comparten comportamiento. Los componentes Blazor también reutilizan presentación.

## Cómo leer los comentarios

Cada archivo de código comienza con su responsabilidad general y los métodos principales tienen una explicación breve. Los comentarios describen el comportamiento existente. Los archivos Designer y las migraciones generadas pueden perder sus comentarios si una herramienta los regenera.

Los JSON, imágenes, la solución y los archivos de terceros se explican en el índice: se conserva su formato original. Los resultados bin/obj y los archivos personales de herramientas no forman parte del código a estudiar.
